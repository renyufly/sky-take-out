# 09 测试、调试、构建与交付

当前仓库没有测试代码，因此本章给出应补齐的标准验证流程。能写代码只是开发的一半，另一半是证明代码正确且可以稳定交付。

## 1. 测试分层

### 单元测试

只测试一个类，将 **Mapper 等依赖替换为 Mock**。适合 **Service 业务分支**，运行快。

```java
@ExtendWith(MockitoExtension.class)
class CategoryServiceImplTest {
    @Mock DishMapper dishMapper;
    @Mock SetmealMapper setmealMapper;
    @Mock CategoryMapper categoryMapper;
    @InjectMocks CategoryServiceImpl service;

    @Test
    void shouldRejectDeletionWhenDishExists() {
        when(dishMapper.countByCategoryId(1L)).thenReturn(2);

        assertThrows(DeletionNotAllowedException.class,
                () -> service.deleteById(1L));
        verify(categoryMapper, never()).deleteById(anyLong());
    }
}
```

### Mapper 集成测试

**连接测试数据库**，验证 XML、参数、结果映射和真实 SQL。理想情况下用 Testcontainers 启动与生产相同版本的 MySQL，**测试结束销毁**。

### Controller 测试

使用 **MockMvc 验证路由**、参数绑定、状态码和 JSON：

```java
mockMvc.perform(post("/admin/category")
        .contentType(MediaType.APPLICATION_JSON)
        .content("{\"name\":\"热销\",\"type\":1,\"sort\":1}"))
        .andExpect(status().isOk())
        .andExpect(jsonPath("$.code").value(1));
```

### 端到端测试

**启动完整服务及依赖**，从 HTTP 入口验证关键用户旅程。数量应少而关键，例如登录、下单、支付回调。

## 2. 测试什么

不要只测正常路径。以删除分类为例：

- 不关联任何数据时成功删除；
- 关联菜品时抛业务异常；
- 关联套餐时抛业务异常；
- ID 不存在时行为明确；
- Mapper 抛异常时响应和日志正确。

以事务为例，应**故意让第二次数据库写入失败，验证第一次写入是否回滚**。

测试命名推荐表达“条件＋结果”：`shouldRollbackDishWhenFlavorInsertFails`。

## 3. 手工接口验证

服务启动后可**使用 Knife4j**：`http://localhost:8080/doc.html`。

也可用 curl：

```bash
curl -X POST http://localhost:8080/admin/employee/login \
  -H "Content-Type: application/json" \
  -d '{"username":"your-user","password":"your-password"}'
```

带 token 查询：

```bash
curl "http://localhost:8080/admin/category/page?page=1&pageSize=10" \
  -H "token: your-jwt"
```

手工测试不能替代自动化测试，因为它不可稳定重复，也难以覆盖回归。

## 4. 调试方法

### 从错误现象沿调用链定位

```text
HTTP 状态和响应
  → Controller 是否命中、参数是否正确
  → Service 分支和当前用户 ID
  → Mapper 参数
  → 最终 SQL 和数据库数据
```

### 常见错误

- 404：路径或 HTTP 方法不匹配，Controller 未扫描。
- 400：JSON 格式、参数类型或校验失败。
- 401：token 缺失、过期、签名错误、请求头名称错误。
- 500：未处理异常，查看第一段业务堆栈而不是只看最底部。
- 数据为空：检查当前用户、状态条件、驼峰映射和数据库环境。
- SQL 语法错误：复制 MyBatis 打印的 SQL 参数，在测试库复现。

IDE 断点应放在关键分支和数据变化处。观察变量比无目的逐行单步更有效。

## 5. 日志

项目使用 SLF4J：

```java
log.info("新增分类：{}", categoryDTO);
```

日志级别：ERROR 表示失败，**WARN 表示风险**，**INFO 记录重要业务节点**，DEBUG 用于开发细节。

建议每个请求具有 traceId，并在关键日志带 orderId/userId 等业务标识。禁止打印密码、完整 token、支付密钥、身份证和不必要的个人信息。

不要使用字符串拼接：占位符可避免未开启对应日志级别时的无谓计算。

## 6. 构建

标准流程：

```bash
mvn clean verify
```

`verify` 会编译、测试、打包并执行验证阶段。只想构建服务及依赖模块：

```bash
mvn -pl sky-server -am clean package
```

产物通常是：

```text
sky-server/target/sky-server-1.0-SNAPSHOT.jar
```

运行：

```bash
java -jar sky-server/target/sky-server-1.0-SNAPSHOT.jar \
  --spring.profiles.active=prod
```

## 7. 交付前配置与数据库

- 使用**外部配置或环境变量注入数据库、Redis、JWT、微信密钥**。
- 使用 Flyway/Liquibase 管理建表和变更脚本，而不是人工修改生产库。
- 数据库变更要可回滚或至少有可靠恢复方案。
- 配置**连接池大小**、SQL 超时、HTTP 超时。
- **设置 JVM 内存、时区和优雅停机**。
- 日志输出到集中系统，并配置指标和告警。

## 8. 健康检查与可观测性

生产项目通常引入 **Spring Boot Actuator，提供健康状态和指标**。至少监控：

- 请求量、延迟、错误率；
- JVM 堆、GC、线程数；
- 数据库连接池使用率和慢 SQL；
- Redis 延迟、命中率；
- 订单创建/支付成功等核心业务指标；
- 定时任务成功、失败和耗时。

日志告诉你发生了什么，指标告诉你系统是否异常，链路追踪告诉你慢在哪里。

## 9. 上线策略

常见发布方式：滚动发布、蓝绿发布、金丝雀发布。发布前执行数据库迁移和自动化测试，发布后验证健康检查和核心接口；出现异常时能够快速回滚应用版本。

接口和数据库变更要向后兼容。例如先让新代码同时兼容旧列和新列，再迁移数据，最后移除旧列，避免应用与数据库发布顺序导致故障。

## 10. 本项目建议优先补的测试

1. `CategoryServiceImpl.deleteById` 的两个拒绝分支。
2. `DishServiceImpl.saveWithFlavor` 的主键回填和事务回滚。
3. `DishServiceImpl.updateWithFlavor` 增加事务后的回滚测试。
4. `OrderServiceImpl.submitOrder` 的空地址、空购物车和三表一致性。
5. JWT 过期、错误签名、无 token 的 401 测试。
6. 支付回调重复通知的幂等测试。
7. Redis 命中、未命中、空结果和失效测试。
8. 订单定时任务的 15 分钟/1 小时时间边界测试。

## 11. 面试表达

当面试官问“你如何保证代码质量”，可以回答：

> 我会先把业务规则写成可验证的正常、边界和异常场景。Service 用单元测试覆盖分支和交互，Mapper 用真实 MySQL 集成测试验证 SQL，Controller 用 MockMvc 验证协议，关键链路再做少量端到端测试。构建执行 clean verify，数据库变更用迁移工具管理；上线后通过日志、指标和链路追踪观察错误率、延迟及核心业务指标。
