# 02 业务场景替换与代码映射

## 1. 新场景：限量活动与场馆预约履约

业务角色：

- 运营人员：创建活动、场馆、场次、库存、价格和预约规则；
- 用户：浏览活动、选择场次、**提交预约**、支付或取消；
- 核销人员：**验证预约码并完成入场核销**；
- 系统：超时释放库存、发送通知、生成报表。

这个场景能自然产生高并发热点，又保留当前项目绝大多数分层和数据访问写法。

## 2. 不要只改类名

必须增加有场景辨识度的业务规则：

- **同一用户同一场次只能预约一次**；
- 场次具有总库存、可用库存、锁定库存；
- 预约资格可包含实名、会员等级、年龄或地域限制；
- 预约创建后 **N 分钟内支付，否则释放库存**；
- **核销码一次有效**，并记录核销设备和人员；
- **场次取消后批量退款和通知**；
- **热门场次采用排队/异步确认**，而普通场次同步落单。

## 3. 领域模型

建议逐步替换为：

```text
activity_category  活动分类
venue             场馆
activity          活动
session           活动场次
session_inventory 场次库存
participant       参与人/实名信息
reservation       预约主表
reservation_item  预约明细和价格快照
reservation_event 状态变更审计
verification      核销记录
```

预约状态机：

```text
排队中 → 待支付 → 已确认 → 待核销 → 已完成
  │         │          ├────────→ 已退款
  └→ 失败   └→ 已取消  └────────→ 已取消
```

每次状态变更需要校验旧状态，并记录事件审计。

## 4. 核心表设计

```sql
CREATE TABLE session_inventory (
    session_id        BIGINT PRIMARY KEY,
    total_stock       INT NOT NULL,
    available_stock   INT NOT NULL,
    locked_stock      INT NOT NULL DEFAULT 0,
    sold_stock        INT NOT NULL DEFAULT 0,
    version           INT NOT NULL DEFAULT 0,
    update_time       DATETIME NOT NULL
);

CREATE TABLE reservation (
    id                BIGINT PRIMARY KEY,
    reservation_no    VARCHAR(32) NOT NULL,
    request_id        VARCHAR(64) NOT NULL,
    user_id           BIGINT NOT NULL,
    session_id        BIGINT NOT NULL,
    quantity          INT NOT NULL,
    amount            DECIMAL(10,2) NOT NULL,
    status            TINYINT NOT NULL,
    expire_time       DATETIME,
    create_time       DATETIME NOT NULL,
    update_time       DATETIME NOT NULL,
    UNIQUE KEY uk_reservation_no (reservation_no),
    UNIQUE KEY uk_request_id (request_id),
    UNIQUE KEY uk_user_session (user_id, session_id),
    KEY idx_session_status (session_id, status),
    KEY idx_expire_status (expire_time, status)
);
```

唯一索引是最终一致性的最后防线；Redis 中的防重复不能替代数据库约束。

## 6. 推荐代码包结构

在保留单体时可按业务模块组织，而不是所有 Controller 放一起：

```text
com.example.booking
├── activity
│   ├── controller
│   ├── service
│   ├── mapper
│   └── model
├── reservation
├── inventory
├── verification
├── notification
└── common
```

这种“按领域聚合、领域内分层”的结构比纯技术分包更适合项目增长。

## 7. 普通预约链路

低流量场次可以同步完成：

```text
校验用户与场次
→ 使用条件 UPDATE 扣 MySQL 库存
→ 插入预约单和明细
→ 提交事务
→ 事务提交后发送通知事件
```

库存 SQL：

```sql
UPDATE session_inventory
SET available_stock = available_stock - #{quantity},
    locked_stock = locked_stock + #{quantity},
    version = version + 1
WHERE session_id = #{sessionId}
  AND available_stock >= #{quantity};
```

影响行数为 0 表示库存不足。无需先查询再扣减，避免并发窗口。

## 8. 热门预约链路

```text
客户端 requestId
→ 网关限流
→ Redis Lua 原子资格/库存判断
→ Kafka reservation-requested
→ 快速返回 QUEUING
→ 消费者落 MySQL 预约单
→ reservation-confirmed / failed
→ WebSocket/轮询返回最终结果
```

异步链路牺牲即时一致性，换取削峰和更高吞吐。客户端必须接受“排队中”状态，不能在接口返回时就展示“预约成功”。

## 9. 迁移步骤

1. 先复制业务概念表，不立即删除旧类。
2. 实现活动、场次、库存和预约的最小同步链路。
3. 加唯一索引、状态条件更新和自动化测试。
4. 将热门读取切换到 Redis。
5. 将热门预约切到 Redis + Kafka 异步链路。
6. 增加核销、超时释放、通知和报表。
7. 删除旧外卖命名和无关逻辑，更新 API 文档。
8. 生成测试数据并执行完整压测。

完成前四步就已经不是简单改名，而是一个可讲清的独立项目。
