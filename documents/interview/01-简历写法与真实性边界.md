# 01 简历写法与真实性边界

## 1. 为什么不直接写“苍穹外卖”

“苍穹外卖”作为教学项目辨识度很高，面试官容易默认它来自课程。问题不在外卖场景本身，而在于大量候选人的描述完全相同：员工管理、菜品 CRUD、购物车、订单、Redis 缓存。

真正能突出的是：

- 你选择了什么业务难点；
- 为什么采用某个技术方案；
- 如何处理一致性、并发、失败和扩容；
- 如何验证结果；
- 你发现并修复了哪些真实问题。

只替换名词、代码和数据模型完全不变，面试深入两问就会暴露。因此需要完成真实改造。

## 2. 推荐项目名称

可选名称：

- `SlotFlow` 限量活动与场馆预约平台；
- `EventHub` 活动预约与履约平台；
- `VenuePass` 场馆预约及核销系统；
- 中文简历：**限量活动预约与履约平台**。

推荐描述：

> 面向场馆、展览与培训活动的预约履约平台，支持活动与场次管理、限量预约、超时释放、支付/取消、入场核销和运营报表。针对热门场次设计 Redis 原子库存与 Kafka 异步削峰链路，并通过容器化和 Kubernetes 实现可观测、可扩缩的部署。

## 3. 简历项目结构

一段项目经历建议包含四部分：

### 项目简介

一到两句话说明用户、业务和规模，不列技术名词。

### 技术栈

只列实际使用：Java 8/17、Spring Boot、MyBatis、MySQL、Redis、Kafka、Docker、Kubernetes、Prometheus/Grafana 等。

### 个人职责

明确你负责的模块和决策，不要用“参与了整个系统开发”。

### 技术亮点

使用“问题—方案—验证结果”表达：

```text
针对什么问题
→ 为什么选择这个方案
→ 如何保证正确性与失败恢复
→ 在什么环境下取得什么实测结果
```

## 4. 基础版简历写法

适合只完成单体业务改造、尚未加入 Kafka/K8s 时：

> **限量活动预约与履约平台｜后端开发**  
> 技术栈：Spring Boot、MyBatis、MySQL、Redis、JWT、WebSocket
>
> - 基于分层架构实现活动、场次、参与人、预约单、核销及运营报表，使用 DTO/Entity/VO 隔离接口与持久化模型。
> - 设计预约状态机和订单号幂等约束，以事务完成预约单、明细和待预约清单的原子写入；通过条件更新避免并发状态覆盖。
> - 使用 Redis Cache Aside 缓存活动和场次数据，设置随机 TTL 并缓存空值，降低热点查询对 MySQL 的压力；更新后删除对应缓存保证最终一致性。
> - 通过 JWT 拦截器完成双端认证，使用 ThreadLocal 传递当前用户并在请求结束后清理；统一业务异常、错误码和接口响应。

## 5. 高并发版简历模板

以下数字必须替换为真实压测结果：

> **限量活动预约与履约平台｜后端开发**  
> 技术栈：Spring Boot、MyBatis、MySQL、Redis、Kafka、Docker、Kubernetes、Prometheus、Grafana
>
> - 针对热门场次瞬时预约流量，使用 Redis Lua 将“库存校验、重复预约校验、库存扣减”合并为原子操作，并以 `requestId` 和用户维度幂等键拦截重复请求；并发压测下未出现超卖。

> - 将活动查询由数据库读取改为 Redis Cache Aside，在“固定环境、固定数据集、持续 N 分钟”的压测中，吞吐由 `[实测前值]` 提升至 `[实测后值]` QPS，P99 从 `[实测前值]` 降至 `[实测后值]` ms，缓存命中率达到 `[实测值]%`。
> - 使用 Docker 构建多阶段镜像，在 Kubernetes 上配置 readiness/liveness probes、requests/limits、滚动升级与 HPA；通过 Prometheus/Grafana 监控 QPS、P95/P99、错误率、Kafka lag、Redis 命中率和 JVM 指标。

## 6. 可量化但不能造假的内容

可以量化：

- 峰值稳定 QPS；
- P50、P95、P99 延迟；
- 错误率和超时率；
- Redis 命中率；
- Kafka 消费延迟和最大 lag；
- 数据库 TPS、慢 SQL 数、连接池使用率；
- CPU、内存、GC 暂停；
- 扩容前后吞吐变化；
- 镜像大小、启动时间、发布耗时；
- 故障恢复时间 RTO、可接受数据损失 RPO。

不建议写：

- “性能提升 300%”但没有基线、环境和报告；
- “支持百万并发”但实际只是插入百万条测试数据；
- “零丢失、零故障”这种无法证明的绝对表述；
- “使用 K8s 实现高可用”但只有一个 Pod、没有探针和故障演练；
- “Kafka 保证消息不丢失”但说不清 producer ack、复制、offset 和消费幂等。

## 7. 面试中的真实性分层

可以这样回答尚未落地的部分：

> 当前我完成了 Redis 原子库存和 Kafka 异步落单，并在本地三节点容器环境做了压测。Kubernetes 部分完成了 Deployment、探针和 HPA 配置；多可用区与分库分表属于下一阶段设计，我在容量达到单库瓶颈前不会过早引入。

这种表达比声称所有技术都已生产落地更可信，也体现演进思维。

## 8. 从当前项目可直接讲的代码审查成果

即使中间件尚未全部实现，也可以真实描述：

- 发现 `DishMapper.xml` 将 `concat` 误写为 `contact`，补充动态分支测试。
- 发现多表更新 `updateWithFlavor` 缺少事务，补充回滚测试。
- 发现请求结束未清理 ThreadLocal，增加 `afterCompletion` 清理。
- 发现支付回调依赖 JWT 用户上下文，改为验签后按商户订单号定位订单。
- 发现定时任务计算了一小时前时间但查询未使用，增加时间边界测试。
- 识别循环查询口味导致 N+1，改为批量查询并按 dishId 分组。

这些内容比“熟悉 Spring Boot”更具体。
