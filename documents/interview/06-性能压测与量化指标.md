# 06 性能压测与量化指标

## 1. 先理解指标

- QPS/RPS：每秒完成的请求数。
- 并发数：同一时刻正在处理的请求或虚拟用户，不等于 QPS。
- P95：95% 请求延迟不超过该值。
- P99：99% 请求延迟不超过该值，反映尾延迟。
- 错误率：失败请求/总请求，必须明确是否包含业务拒绝。
- 吞吐：单位时间处理的数据量。
- 饱和点：继续增加负载时吞吐不再增长、延迟和错误率快速恶化的位置。

平均延迟会掩盖慢请求，简历优先报告 P95/P99，同时给出 QPS 和错误率。

## 2. 不要直接承诺一个数字

“系统 P99 是 100 ms”没有意义，必须附带：

- 硬件：CPU、内存、节点数；
- 组件规模：应用 Pod、MySQL、Redis、Kafka；
- 数据量和热点比例；
- 接口与读写比；
- 并发模型和压测时长；
- 是否包含网络、鉴权和响应体；
- 错误率、资源使用率和 GC；
- 测试工具是否与服务部署在不同机器。

## 3. 建议 SLO（目标，不是实测）

以下是适合个人项目的示例验收目标，不能直接当成结果：

| 场景 | 示例目标 |
| --- | --- |
| 活动详情缓存命中 | P95 < 80 ms，P99 < 150 ms，错误率 < 0.1% |
| 活动搜索/数据库分页 | P95 < 200 ms，P99 < 400 ms |
| 热门预约资格接口 | P95 < 100 ms，P99 < 200 ms，业务超卖数 = 0 |
| Kafka 异步落单 | 99% 成功事件在 3 秒内落库 |
| 取消/释放库存 | P99 < 500 ms，最终库存对账差异 = 0 |
| 系统可用性 | 月度目标 99.9%（个人项目通过故障演练验证关键路径） |

目标要根据机器和业务调整。P99 目标过低却使用跨网络数据库和大型响应，反而显得不可信。

## 4. 容量估算示例

假设一个热门活动：

- 10 万用户在 5 分钟内进入详情页；
- 峰值系数取平均值的 5 倍；
- 每人详情页产生 3 个请求；
- 2 万人提交预约，集中在 30 秒；
- 库存 3000。

估算：

```text
详情平均 RPS = 100000 × 3 / 300 = 1000
详情峰值 RPS ≈ 1000 × 5 = 5000
预约平均 RPS = 20000 / 30 ≈ 667
可按 3 倍突发准备 ≈ 2000 RPS
最终成功预约 = 3000，不能超过库存
```

容量估算给压测负载提供依据，不代表系统已经达到该容量。

## 5. 压测场景

### 场景 A：缓存读取

- 95% 热点活动、5%随机活动；
- 分别测试缓存预热和冷启动；
- 记录命中率、Redis 延迟和 MySQL QPS。

### 场景 B：秒杀预约

- 库存固定 3000；
- 2 万个不同用户与一定比例重复请求；
- requestId 有正常和重放两组；
- 验证成功数、重复数、售罄数以及最终数据库库存。

### 场景 C：混合流量

```text
70% 活动浏览
15% 场次查询
10% 预约
3% 取消
2% 结果查询
```

混合场景比单接口更接近真实资源竞争。

### 场景 D：故障压测

- 压测中重启一个应用 Pod；
- 制造 Redis 短暂不可用；
- 暂停 Kafka 消费者再恢复；
- 注入 MySQL 延迟；
- 观察错误率、P99、lag、恢复时间和数据一致性。

## 6. 负载模型

推荐阶段：

```text
预热 2 分钟
逐级加压 10 分钟
目标负载稳定 15～30 分钟
短时峰值 3～5 分钟
逐步降压 2 分钟
```

先做 closed model（固定虚拟用户）便于入门，再用 open model（固定到达率）验证服务在既定流量下是否排队。

压测机本身不能满 CPU/网络，否则测到的是压测工具瓶颈。

## 7. k6 脚本骨架

```javascript
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    booking: {
      executor: 'ramping-arrival-rate',
      startRate: 100,
      timeUnit: '1s',
      preAllocatedVUs: 200,
      maxVUs: 2000,
      stages: [
        { target: 500, duration: '2m' },
        { target: 1000, duration: '5m' },
        { target: 1000, duration: '10m' }
      ]
    }
  },
  thresholds: {
    http_req_failed: ['rate<0.001'],
    http_req_duration: ['p(95)<100', 'p(99)<200']
  }
};

export default function () {
  const requestId = `${__VU}-${__ITER}`;
  const response = http.post('http://host/api/reservations/qualify',
    JSON.stringify({ sessionId: 2001, quantity: 1, requestId }),
    { headers: { 'Content-Type': 'application/json', Authorization: 'Bearer ...' } });
  check(response, { 'accepted or sold out': r => [200, 409].includes(r.status) });
}
```

示例中的 threshold 是目标，执行前需要根据环境调整。业务售罄 409 不应简单计入系统错误率。

## 10. 如何定位 P99 过高

按证据排查：

1. 客户端到网关、应用、Redis/MySQL/Kafka 的分段耗时；
2. JVM GC pause、线程池排队、CPU throttling；
3. 数据库慢 SQL、锁等待、连接池 pending；
4. Redis 慢命令、大 key、连接池等待；
5. Kafka producer batch/ack、消费者处理和 lag；
6. 日志同步写、序列化和大响应体；
7. 单个热点分区或热点 key。

优化后必须用相同环境和脚本复测，才能得出可比较结论。
