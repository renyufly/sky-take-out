# 08 面试问答与项目陈述

## 1. 30 秒项目介绍

> 我基于一个 Spring Boot 教学项目完成了业务重构，将普通外卖场景改造成限量活动与场馆预约平台。系统支持活动场次、限量预约、超时释放、支付取消和核销。我重点实现了 Redis Lua 原子资格与库存预扣、Kafka 异步落单和幂等消费，并使用 Docker/Kubernetes 做可观测部署。所有性能数字都来自固定环境下的 k6 压测，我同时记录 P95/P99、错误率、Kafka lag 和库存一致性，而不是只看平均 QPS。

## 2. 两分钟项目介绍模板

> 最初项目是典型的 Controller-Service-Mapper 单体。我先修复了多表更新缺事务、ThreadLocal 未清理、支付回调依赖登录上下文和 N+1 查询等问题，并增加状态条件更新、唯一索引和自动化测试。
>
> 为增加业务辨识度，我重构为限量活动预约场景。普通场次通过 MySQL 条件更新扣库存；热门场次先在网关限流，再用 Redis Lua 原子完成 requestId 幂等、用户防重和库存预扣，成功后发送 Kafka 事件。消费者在数据库事务内进行事件去重、最终库存校验和预约落单，数据库提交后提交 offset；失败通过重试/死信和幂等补偿处理。客户端先得到排队状态，再通过查询或 WebSocket 获得最终结果。
>
> 部署方面我使用 Docker 构建镜像，在 Kubernetes 配置探针、资源请求、滚动更新和 HPA，并用 Prometheus/Grafana 观测 HTTP 分位延迟、JVM、数据库连接池、Redis 命中率和 Kafka lag。最后用 k6 在明确的硬件与数据规模下进行阶梯和故障压测，实际结果是 `[填写真实值]`。

## 3. 为什么换成预约平台

回答要点：

- 外卖 CRUD 教学项目同质化高；
- 预约场景能保留已有分层和订单能力，降低无意义重写；
- 限量场次自然产生库存、防重复、排队、超时释放和核销问题；
- 中间件是由业务问题驱动，而不是为了堆技术栈。

## 4. 为什么 Redis 能防超卖

> 普通 GET 再 SET 存在竞态。我使用 Lua 把请求幂等、用户防重、库存判断和扣减放在 Redis 单次原子执行中，只有获得资格的请求才能进入 Kafka。Redis 不是最终事实源，MySQL 仍有唯一索引和条件库存更新兜底；落单失败会执行幂等补偿，并通过对账任务发现差异。

追问：Redis 宕机怎么办？

> 热门预约会快速失败或进入受控排队，不直接降级打 MySQL，避免缓存故障扩大为数据库故障。恢复时根据 MySQL 预约、事件和资格记录对账重建。

## 5. 为什么使用 Kafka

> 峰值资格请求可能超过 MySQL 持续写能力。Kafka 让入口快速接受请求并削平写入峰值，同时将预约、通知和统计解耦。代价是最终一致性和更复杂的失败处理，因此我实现了可靠生产、幂等消费、手动提交 offset、重试/死信、lag 监控和对账，而不是认为接入 MQ 就自动可靠。

追问：如何保证消息不丢？

> 生产端等待发送结果，设置可靠确认和副本策略；Redis 与 Kafka 双写失败有补偿或可靠待发送记录；消费端数据库提交后再提交 offset。仍然需要对账，因为跨 Redis、Kafka、MySQL 无法靠单一事务自动保证端到端零丢失。

## 6. 如何处理重复消费

> Kafka 至少一次语义下重复是正常情况。事件有 eventId，预约请求有 requestId；数据库对 eventId、requestId 和 userId+sessionId 建唯一约束。消费逻辑在同一事务内先去重再写预约，重复消息按已处理成功返回，因此数据库提交后 offset 未提交导致的重复不会重复创建预约。

## 7. 如何保证顺序

> Kafka 只保证分区内有序。如果业务要求同一场次的状态事件有序，就以 sessionId 作为 key；如果 Redis 已完成资格排序且落单只需幂等，可选更分散的 key 避免热点分区。数据库状态更新还会带旧状态条件，不能只依赖消息顺序保证正确性。

## 8. 缓存和数据库如何一致

> 活动详情使用 Cache Aside：读先缓存，未命中查数据库并回填；写先提交数据库再删除缓存。Redis 库存是高并发资格层，MySQL 是最终事实源，通过成功/失败事件、幂等补偿和定期对账达到最终一致。不同数据的一致性要求不同，活动描述可短暂陈旧，库存不能超卖。

## 9. `@Transactional` 有什么坑

回答：基于代理；自调用、非 Spring Bean、private 方法、异常被吞、受检异常未配置、跨线程/跨服务等情况可能不生效。数据库事务不能自动覆盖 Redis、Kafka 和 WebSocket。

结合项目：`updateWithFlavor` 的更新、删除旧口味、插入新口味应在同一事务；WebSocket 不应在数据库事务提交前作为不可撤销副作用发送。

## 11. 为什么使用 Kubernetes

> 目标不是为了有 K8s 名词，而是统一部署、健康检查、滚动升级、资源隔离和按指标弹性扩容。我为 API 配置 startup/readiness/liveness，按 CPU/RPS 扩容；消费者按 Kafka lag 扩容。压测中验证扩容速度、P99、下游连接池和 Pod 故障恢复。MySQL/Redis/Kafka 的生产高可用由托管服务或独立集群承担，不把单副本 StatefulSet 描述成高可用。

## 12. 系统当前瓶颈在哪里

成熟回答不应猜：

> 需要看压测证据。如果 API CPU 低但连接池 pending 高，瓶颈可能是数据库；如果 Kafka lag 只集中在一个分区，是热点 key；如果 Pod CPU throttling 且 P99 抖动，是资源 limit 或 JVM 问题。我会同时看分段追踪、GC、线程池、数据库慢 SQL、Redis 延迟和 Kafka lag，再决定优化。

## 13. 如何扩展到十倍流量

回答框架：

1. 先复核读写比例和峰值估算。
2. CDN/Redis 承担热点读，避免所有流量进入应用和数据库。
3. API 无状态水平扩展，网关限流和负载均衡。
4. 热门写进入 Redis + Kafka，消费者按下游能力扩展。
5. 优化索引、批量写、连接池；必要时读写分离。
6. 单库达到证据充分的容量瓶颈后再选择分片键。
7. 完整监控、降级、故障演练和容量预案。

## 16. 最终提醒

面试官很容易沿着名词追问：

```text
用了 Redis → 为什么原子 → Cluster 多 key 怎么办 → 宕机如何恢复
用了 Kafka → 什么语义 → 重复怎么办 → 积压怎么办 → 分区怎么选
用了 K8s → 探针区别 → 如何扩容 → 下游撑得住吗 → 如何优雅停机
写了 P99 → 什么环境 → 什么流量 → 错误怎么算 → 报告在哪里
```

只有当每条都能用代码、配置、监控或报告证明时，才把它写成“已实现”。否则明确写为“设计”或“规划”。
