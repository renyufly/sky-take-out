# 01 项目全景与 Java 后端开发流程

## 1. 项目是什么

该项目是一个 Maven 多模块 Spring Boot 后端：

```text
sky-common  公共常量、异常、工具、配置属性、统一响应
sky-pojo    Entity、DTO、VO
sky-server  Controller、Service、Mapper、配置及启动类
```

依赖方向是 `sky-server → sky-common + sky-pojo`。父工程根 `pom.xml` 统一管理依赖版本，`sky-server` 是真正可运行的模块。

启动入口：`sky-server/src/main/java/com/sky/SkyApplication.java`。

```java
@SpringBootApplication
@EnableTransactionManagement
@EnableCaching
@EnableScheduling
public class SkyApplication {
    public static void main(String[] args) {
        SpringApplication.run(SkyApplication.class, args);
    }
}
```

- `@SpringBootApplication` 包含配置、自动配置和组件扫描。
- 默认扫描启动类所在包 `com.sky` 及其子包。
- `@EnableTransactionManagement` 开启注解事务。
- `@EnableCaching` 开启 Spring Cache。
- `@EnableScheduling` 开启 `@Scheduled` 定时任务。

## 2. 一个请求怎样经过后端

以 `GET /admin/category/page?page=1&pageSize=10` 为例：

```text
HTTP 请求
  ↓
JwtTokenAdminInterceptor：校验 token，保存员工 ID
  ↓
CategoryController.page：绑定查询参数
  ↓
CategoryServiceImpl.pageQuery：启动分页并组织业务
  ↓
CategoryMapper.pageQuery：执行 SQL
  ↓
MySQL：返回记录
  ↓
PageResult → Result.success(pageResult) → JSON
```

对应源码：

- Web 配置：`sky-server/.../config/WebMvcConfiguration.java`
- Controller：`sky-server/.../controller/admin/CategoryController.java`
- Service：`sky-server/.../service/impl/CategoryServiceImpl.java`
- Mapper：`sky-server/.../mapper/CategoryMapper.java`
- SQL：`sky-server/src/main/resources/mapper/CategoryMapper.xml`

## 3. 为什么要分层

### Controller：处理 HTTP

职责包括**接收参数、调用 Service、返回响应**。不要在这里写复杂 SQL 或大段业务判断。

### Service：处理业务

职责包括业务校验、**流程编排**、事务边界、**调用一个或多个 Mapper**。

例如删除分类前，`CategoryServiceImpl.deleteById` 会检查分类是否关联菜品或套餐。这是业务规则，应该放在 Service。

### Mapper：处理持久化

职责是**把 Java 方法映射为 SQL**。Mapper 不应该决定“启售菜品不能删除”这种业务规则。

### DTO / Entity / VO：隔离数据模型

```text
客户端 JSON → DTO → Service → Entity → 数据库
数据库结果 → Entity/VO → Result → 客户端 JSON
```

分开建模可以**避免客户端直接控制数据库中的敏感字段**，也能让**返回结构不受表结构限制**。

## 4. 从零开发一个功能的标准流程

假设需求是“新增优惠券分类”：

1. **明确业务规则**：名称是否唯一、状态有哪些、能否删除。
2. 设计**表**：字段类型、非空、默认值、唯一索引、普通索引。
3. 设计 **API**：URL、HTTP 方法、请求参数、响应、错误情况。
4. **创建 DTO**：只接收客户端允许提交的字段。
5. 创建 **Entity**：**映射数据库**字段。
6. 创建 Mapper：先写最小 SQL，再补动态查询和批量操作。
7. 创建 Service：实现规则和事务。
8. 创建 Controller：参数绑定、日志、调用 Service、统一响应。
9. 补全异常、权限、缓存失效和接口文档。
10. 测试正常、边界、异常、并发和回滚场景。

推荐顺序是**先从数据库和业务规则出发，再写 Controller**；不要从“先加一个接口”开始盲目向下堆代码。

## 5. Spring Boot 自动配置到底做了什么

项目引入 `spring-boot-starter-web` 后，Spring Boot 会根据 classpath 自动配置：

- 内嵌 Tomcat；
- Spring MVC 的 `DispatcherServlet`；
- JSON 序列化；
- 常见错误处理；
- 配置文件加载。

项目引入 MyBatis Starter、Redis Starter 后，又会自动创建相关基础设施 Bean。自动配置不是“魔法”，本质是**根据条件注解决定是否注册配置类和 Bean**。

面试表达：Spring Boot 通过 starter 聚合依赖，通过自动配置减少样板配置，通过外部化配置支持不同环境。

## 6. 配置文件与环境

`application.yml` 定义通用配置，并通过：

```yaml
spring:
  profiles:
    active: dev
```

加载 `application-dev.yml`。数据库 URL 又引用自定义属性：

```yaml
url: jdbc:mysql://${sky.datasource.host}:${sky.datasource.port}/${sky.datasource.database}
```

常见生产实践：

- 开发、测试、生产使用不同 profile；
- 密码和密钥通过环境变量或配置中心注入；
- 不把真实凭据提交到 Git；
- 生产环境关闭过多 SQL 日志。

## 7. 项目的优点与可改进点

优点：分层直观、业务覆盖完整、同时展示 MyBatis、Redis、JWT、事务、AOP、WebSocket 和定时任务。

可改进：

- 多数依赖使用字段注入，生产项目更推荐**构造器注入**。
- DTO 缺少 Bean Validation 参数校验。
- `Result` 只用业务 code，错误响应可进一步结合 HTTP 状态码。
- 缺少数据库迁移脚本和自动化测试。
- `ThreadLocal` 设置后没有在拦截器完成阶段显式 `remove()`，线程池复用时有污染风险。
- 部分复杂逻辑和支付回调需要加强幂等、鉴权和异常处理。

面试时不要贬低项目，而应说：“这个教学项目展示了核心链路；若用于生产，我会从校验、测试、安全、幂等和可观测性几个方面增强。”
